# Design

## Context

See `proposal.md` for motivation. The local Mind2Web root chunks contain 1,009 unique training tasks, 73 website names, and 7,775 actions. The `website` field identifies the site; `domain` and `subdomain` are broad task categories and must not be used as the split key. The repo also contains `train`, `val`, and `test` fixture folders generated by the current downloader. The 19,500-step checkpoint uses the existing six-action configuration.

`RealWebTrajectoryDataset` currently partitions chunk rows by order, can repeat tasks to fill `dataset_size`, creates fallback annotations, and falls back to procedural templates. `download_mind2web.py` checks connectivity but can emit its built-in fixtures instead of downloaded data. `run_ablation.py` uses `AgentTrajectoryDataset`, one seed, 300 steps by default, and writes to the shared `ABLATION_REPORT.md`. The existing offline evaluator also permits the dataset fallback.

## Goals / Non-Goals

**Goals:**

- Use the available Mind2Web training traces only for the real-data cohort; preserve provenance and exclude generated fixture folders.
- Produce deterministic website-disjoint manifests with at least 50 training websites and 10 websites each for validation and test.
- Train all four parameter-matched architectures from fresh initialization, with the same examples, update budget, optimizer schedule, and three seeds; give each seed three passes over unique training tasks.
- Preserve `SELECT` as an action class in new ablation models, while retaining the legacy six-class configuration for the existing checkpoint.
- Save enough run metadata, metrics, and checkpoints to reproduce and inspect the comparison without overwriting prior artifacts.

**Non-Goals:**

- Continuing or converting the step-19,500 checkpoint into one of the matched baselines.
- Claiming official Mind2Web benchmark results from a split derived from the training set. Official test data are not present in the local raw corpus.
- Claiming closed-loop live-web task success from offline recorded-trace replay.
- Adding WebLINX or treating WebArena task definitions and generated HTML as authentic interaction traces.

## Decisions

1. **Make real and fixture modes explicit.** The downloader and dataset APIs will identify source mode and provenance. Real mode accepts trace files with authentic observations and recorded actions, stamps source/version/split/file hashes, and errors when usable traces are absent. The fixture generator remains available only through an explicit fixture mode and emits synthetic provenance. The ablation and real-data evaluation select real mode and never silently fall back. The checked-in report contains aggregate counts and hashes, not raw HTML or task text; raw data and run outputs remain under ignored data/run directories.

2. **Build a content-addressed manifest before parsing examples.** A preparation pass inventories record IDs, normalized `website` identities, upstream split labels, action coverage, and snapshot hashes. It assigns complete sites to a deterministic 70/15/15 train/validation/test split, stratifying by broad domain category and reporting subdomain coverage, and checks duplicate IDs and shared snapshots. The manifest stores IDs and provenance metadata, not page content. If the 50/10/10 website floor cannot be met, training stops. Cache keys include the manifest checksum and real/fixture mode. Real mode emits each unique task once per epoch and applies no spatial augmentation or padding-by-duplication.

3. **Treat missing labels as missing.** Parse the source operation and argument without coercing `SELECT` to `CLICK`. Use only a uniquely annotated original target for element and coordinate supervision. When rationale, target, geometry, or observation is absent or ambiguous, mask the relevant loss and metric and record the count; never synthesize a thought, HTML snapshot, target element, or bounding box. Existing fixtures may keep their synthetic defaults in explicit fixture mode.

4. **Match the four architectures by instantiated trainable parameter count.** Calibrate the dense and expert intermediate widths to the Full JED-M2 parameter budget, then confirm the actual counts are within 1%. All four ablation configs use seven output classes with `SELECT` appended at index 6. The base legacy config remains six-class, so the old checkpoint loads in its original shape and is reported separately. Each seed resets initialization and uses the same deterministic example order for all four models. Each model sees three complete passes over the unique training manifest, with a common batch/gradient-accumulation schedule and optimizer settings. Results record tokens, updates, parameters, elapsed time, and peak memory so differences in per-step compute remain visible.

5. **Use a sequential run coordinator and isolated output directory.** `run_ablation.py` creates a unique directory under `runs/ablation/`, refuses collisions, and writes a run manifest before training. It trains one model/seed at a time, saves its final checkpoint and per-step metrics, then frees accelerator memory. The final Markdown and JSON reports aggregate per-seed results and website-macro plus overall-micro metrics. Memory and latency profiles remain architecture measurements and are identified as such. A path collision is an error unless the user explicitly requests overwrite.

6. **Score internal held-out sites honestly.** The evaluation runner consumes the same split manifest and verifies website disjointness. It reports action accuracy, target-element hit rate, coordinate error/tolerance, step accuracy, exact full-trajectory match rate, and per-website coverage. It labels these as offline trace-replay results and reports macro-average-by-website and micro-average separately. The step-19,500 checkpoint is a legacy reference without SELECT output; its results are not mixed into the matched-baseline aggregate.

## Risks / Trade-offs

- **The custom test sites come from the available training corpus.** This supports an internal cross-site comparison but not official benchmark claims; report the split as custom and keep official test files out of training.
- **Some traces lack rationale or unambiguous original target geometry.** Masking reduces the number of examples for those losses; publish coverage and denominators alongside scores.
- **Three seeds and three passes require 36 model-seed-epochs across four architectures.** Run sequentially, save progress per model/seed, and permit safe resumption without reusing a different manifest or config.
- **The legacy checkpoint cannot predict SELECT.** Preserve its six-class shape and label it as a separate reference rather than altering checkpoint weights.
- **Mind2Web data redistribution is restricted by its maintainers.** Keep raw data outside version control and do not copy page content into reports or committed manifests.

## Migration Plan

No existing raw data or checkpoint is modified or deleted. The existing fixture generator remains opt-in. New manifests, caches, checkpoints, and reports use a unique ignored run directory. To roll back, select the legacy synthetic mode and keep the existing report/checkpoint paths; the new run outputs remain isolated.
